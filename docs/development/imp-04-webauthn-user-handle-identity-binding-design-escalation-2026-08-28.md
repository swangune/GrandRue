# IMP-04 — WebAuthn User-Handle ↔ Identity Binding Design Escalation

**Date:** 28 August 2026  
**Status:** DESIGN_ESCALATION — MANUAL APPROVAL REQUIRED  
**Implementation target:** IMP-04 Merchant Account, Scope, Identity & Trust  
**Triggered by:** production WebAuthn credential persistence completion  
**Governing authorities reviewed:** MS-PROT-028, MS-PROT-063, MS-PROT-071, ADR-014, ADR-015, MS-IMPLEMENTATION-RULES-001

---

## 1. Trigger

IMP-04 now has durable Main Street-owned persistence for Spring Security WebAuthn `CredentialRecord` values through a `UserCredentialRepository` adapter.

The next apparent implementation child is a production `PublicKeyCredentialUserEntityRepository` and the bridge by which successful WebAuthn authentication resolves to Main Street authenticated `Identity` evidence.

Implementation cannot safely proceed until the meaning and lifecycle of the WebAuthn `user.id` / user handle relative to Main Street `Identity` is explicit.

---

## 2. Accepted authority already determines

The accepted corpus already requires:

- Identity is distinct from authority, Merchant Scope and merchant relationship;
- authentication establishes Identity evidence, not business authority;
- Merchant Controller relationship and Merchant Scope remain current downstream checks;
- WebAuthn is the production Controller ceremony/cryptographic-verification adapter;
- Spring Security session/authority semantics must not become Main Street authority;
- WebAuthn credential persistence is authentication evidence only;
- successful WebAuthn authentication must bridge into Main Street-owned post-authentication session establishment.

These constraints are sufficient to reject several unsafe implementations, but they do not define the identity of the WebAuthn user handle itself.

---

## 3. Missing decision

The corpus does not currently determine whether a WebAuthn user handle is:

1. the byte representation of the Main Street semantic `Identity` identifier;
2. a separate opaque authentication-subject identifier mapped one-to-one to Main Street `Identity`;
3. a credential-local identifier, potentially different across credentials for one Identity; or
4. another lifecycle/cardinality.

This affects authentication, credential ownership, recovery, privacy, deletion/re-registration and historical continuity. Under MS-IMPLEMENTATION-RULES-001 Sections 3, 5 and 6 this is a material authentication/security decision and therefore requires manual approval before production implementation.

---

## 4. External technical constraint

WebAuthn/Spring treat `PublicKeyCredentialUserEntity.id` as the WebAuthn user handle: an opaque, non-empty byte sequence of at most 64 bytes, not intended for display and not suitable for personally identifying information such as username/email.

The handle identifies the relying-party user account for credential registration/authentication. Multiple credentials for the same account are expected to share the account identity represented by that handle.

These protocol/library constraints do not decide Main Street semantic ownership.

---

## 5. Options

### Option A — encode Main Street `Identity` identifier directly as the WebAuthn user handle

**Shape**

```text
Main Street Identity identifier
        =
WebAuthn user handle
```

**Advantages**

- no mapping table;
- simple deterministic resolution;
- one less authentication identifier.

**Risks**

- couples semantic Identity representation to a protocol-facing credential identifier;
- constrains future Identity identifier evolution to WebAuthn size/privacy requirements;
- makes an external authentication identifier carry direct semantic identity representation;
- creates avoidable replacement/migration coupling if WebAuthn or Identity representation changes.

**Assessment:** technically possible but architecturally over-coupled.

### Option B — separate opaque WebAuthn authentication-subject handle mapped one-to-one to Main Street `Identity`

**Shape**

```text
Main Street Identity
        1
        │
        1
WebAuthn authentication subject / user handle
        │
        ├── Credential A
        ├── Credential B
        └── Credential C
```

The handle is generated by Main Street, opaque, non-PII, credential-independent and stable for that WebAuthn subject while the binding is active. It is authentication infrastructure evidence only.

**Advantages**

- preserves Identity as the semantic authority while keeping WebAuthn replaceable;
- satisfies WebAuthn opaque/non-PII requirements cleanly;
- allows multiple passkeys for one Identity without duplicating semantic Identity;
- prevents Spring/WebAuthn technical representation from defining Identity equality;
- permits future authentication-provider changes without changing semantic Identity identifiers.

**Costs**

- requires a durable mapping and uniqueness constraints;
- introduces a narrowly scoped authentication-subject lifecycle that must be kept subordinate to Identity.

**Assessment:** recommended.

### Option C — credential-local user handles

Each credential receives an independent handle and resolves separately to Identity.

**Advantages**

- maximal credential-level isolation.

**Risks**

- does not naturally model WebAuthn's account-level user handle;
- makes multi-passkey account continuity unnecessarily complex;
- risks credential identity becoming account identity;
- complicates discovery, credential management and recovery.

**Assessment:** reject unless a later explicit requirement justifies it.

---

## 6. Recommendation

Approve **Option B**:

> Main Street SHALL own a distinct opaque WebAuthn authentication-subject user handle, mapped one-to-one to one Main Street `Identity`. The handle is authentication infrastructure evidence, not semantic Identity, Merchant Scope, Controller authority, role or privilege. Multiple WebAuthn credentials for one Identity SHALL reference the same active WebAuthn user handle.

Recommended invariants:

1. the handle is generated by Main Street and is not caller-selected;
2. the handle contains no username, email, merchant identifier or other PII/business authority;
3. one active handle maps to exactly one Main Street Identity;
4. one Main Street Identity maps to at most one active WebAuthn handle for the initial implementation;
5. credential registration may add multiple credentials under that handle;
6. successful WebAuthn authentication resolves handle → Identity evidence only;
7. successful authentication still flows through `HumanSessionEstablishmentService` for a fresh Main Street Session Credential;
8. handle possession or knowledge alone grants no authentication or authority;
9. changing Merchant Controller relationships does not change the Identity↔handle binding and is revalidated downstream;
10. credential deletion does not silently delete semantic Identity;
11. recovery/rebinding/rotation semantics remain separately governed where they alter control or trust.

---

## 7. Falsification criteria

The recommendation is invalid if it causes any of the following:

- the WebAuthn handle becomes Merchant Scope or Controller authority;
- a credential identifier becomes equivalent to semantic Identity;
- a username/email/merchant identifier is embedded in the handle;
- one handle can resolve ambiguously to multiple Identities;
- credential registration can silently rebind an existing handle to another Identity;
- removal of one credential destroys unrelated credentials for the same Identity without explicit credential-management semantics;
- Spring `Authentication`/`SecurityContext` bypasses Main Street Session establishment;
- a former Merchant Controller remains authorised because the authentication binding froze merchant authority.

---

## 8. Implementation shape after approval

If approved, the smallest next child should be tests-first and limited to:

```text
MainStreetWebAuthnUserEntityRepository
        +
opaque user-handle persistence/mapping
        +
unique handle ↔ Identity binding
        +
lookup required by Spring WebAuthn
```

It must not yet implement browser endpoints, CSRF, account recovery, global session invalidation, step-up authentication, platform-admin hardware attestation or merchant-authority shortcuts.

A subsequent child can bridge successful verified WebAuthn authentication to the mapped Main Street `Identity` and then into `HumanSessionEstablishmentService`.

---

## 9. Decision required

**Manual approval required before production code proceeds.**

Recommended approval statement:

> Approve Option B: use a separate Main Street-owned opaque WebAuthn user handle mapped one-to-one to Main Street Identity, with multiple credentials sharing that handle and no Merchant Scope/authority semantics in the binding.
