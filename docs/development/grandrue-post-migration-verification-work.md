## 1. Responsibility split and state machine

**Preparation** pins complete inputs, enumerates both trees and claims once, resolves exact identity/provenance, establishes allowed edits independently, classifies the population into immutable-object fast-path entries, deterministic transformation classes and exceptions, and prepares dependency-/claim-closed verification regions. It must not approve a migration difference merely because it is already present.

**Execution** consumes one `READY` closed-region or exception packet, validates its frozen inputs, performs only its declared read-only checks, mechanically emits exact per-file/per-claim evidence, and checkpoints the outcome. It must not rediscover the same mapping for each file, invent a new rename policy, widen the allowlist, repair source files or decide an unresolved semantic question.

```text
PREPARATION_REQUIRED -> PREPARED -> READY -> IN_PROGRESS -> CHECKPOINTED
                                      |
                         stale or unresolved input
                                      v
                         PREPARATION_REQUIRED / BLOCKED
```

A `CHECKPOINTED` packet contains a result of `PASS`, `FAIL` or `BLOCKED`; checkpointing does not mean passing. A failed comparison is a durable result, not an invitation to edit the expected answer. Freshness failure returns the packet to preparation and preserves any previous receipt.

A packet is not `READY` while it contains null required inputs, placeholders, unspecified file sets, unexpanded directory patterns, guessed counts, “rename as appropriate”, “inspect and decide”, or an open authority question.

## 4. GR-VV-01 — enumerate and reconcile every entry

### 4.1 Prefer complete Git object reads

Where a full authorised local repository is available, use immutable Git object reads, not checked-out file contents. Relevant command forms are below; `B`, `D`, `OID` and paths must be resolved into concrete packet arguments before execution.

```bash
# These are command forms, not an already prepared executable packet.
git --no-replace-objects ls-tree -r -z --full-tree "$M"
git --no-replace-objects ls-tree -r -z --full-tree "$D"
git --no-replace-objects cat-file -t "$OID"
git --no-replace-objects cat-file -s "$OID"
git --no-replace-objects cat-file blob "$OID"
git --no-replace-objects diff --raw -z --no-abbrev --no-renames --no-ext-diff --no-textconv "$M" "$D" --
git --no-replace-objects diff --check --no-ext-diff --no-textconv "$M" "$D" --
```

Run from the declared repository root, record exit codes and capture binary stdout without text/newline conversion. Preserve NUL-delimited path output. Read the advertised number of blob bytes and verify the object identity; do not use text-mode redirection or line splitting that changes bytes. Record missing objects, shallow-history limitations, errors and unsupported object types as blockers rather than empty results. The final command is a supplementary diff-integrity check, not a preservation proof. [T1–T3]

Do not use `git diff B...D` as the primary comparison: the required comparison is the two endpoint trees, not the merge-base-to-target change. Rename detection may suggest candidates for human review, but cannot establish identity or complete coverage. [T2]

An authorised GitHub tree/blob API route is also acceptable. Verify `truncated` indicators, all pages/subtrees and every retrieved object's identity. A GitHub compare response is not a complete file inventory; its file list is limited, and recursive tree responses can also be truncated. If necessary, traverse each subtree non-recursively until the complete tree is established. If complete bytes cannot be retrieved through the available authorised access, report `BLOCKED`; never certify an excerpt. [T4–T5]

### 4.2 Inventory boundary

Enumerate every tracked leaf entry regardless of name, extension or directory. Include symlink target bytes and executable modes. For submodules, inventory the gitlink commit and `.gitmodules`; do not claim to have checked the nested repository without separate complete evidence. For Git LFS, distinguish the committed pointer from external payload availability/integrity. Such limitations must be stated in the snapshot and report; any claim that depends on unavailable external content is blocked.

Working-tree files, ignored build outputs, local databases and deployed services are not the committed `B → D` comparison. Do not claim they were audited. No submodule update, LFS mutation, build, package installation or runtime start is implied by this procedure.

### 4.3 Identity mapping

Build a one-to-one endpoint correspondence before declaring any file preserved. Start with exact claim mappings and evidenced pre-migration moves; reconcile same-path entries and identical-object move candidates without allowing either to overwrite an existing mapping. Ambiguous identical copies need independent identity evidence.

For each baseline entry, establish its live counterpart or record an explicit missing-target finding. For each target entry, establish its baseline origin or separately evidenced introduction. Validate destination case, file type, mode and old-path disposition. Check for undeclared duplicate legacy and GrandRue copies.

A file touched by several migration leaves gets one row with multiple claim links and one composed expected transformation. Never compare a shared consumer against only its earliest import edit while ignoring later claimed changes.

Do not certify splits, merges, deletions or arbitrary whole-file replacements as naming-only changes. Record them as findings and seek independently established provenance/authority where appropriate. An intentionally authorised deletion can be accounted for, but cannot be labelled lossless preservation of that baseline file.

### 4.5 Coverage invariants

Let `M_entries` and `D_entries` be all baseline and target leaf entries. Each endpoint key is the exact path, with its object/type/mode retained as evidence. Require:

```text
set(manifest.baseline.path where baseline exists) == set(M_entries.path)
set(manifest.target.path where target exists)     == set(D_entries.path)
each baseline path occurs exactly once on the baseline side
each target path occurs exactly once on the target side
baseline rows represented == baseline entries enumerated
target rows represented   == target entries enumerated
```

Also require exact object/type/mode agreement between each row and its tree entry; no row with both sides absent; no dangling claim, file, transformation or receipt IDs; and no silent omission of an error row. Reconcile the independently derived raw changed-path set against the manifest's changed endpoint entries. Counts alone cannot prove set equality.

Both `enumeration_complete` and the concrete counts must be established before reporting zero unclassified files. Accounting completeness may be true while content results still fail; those facts must remain separate.

## 5. GR-VV-02 — prepare independently justified expectations

### 5.1 Baseline bridge

Optional `B → M` analysis is contextual only. When performed, retain its raw differences separately; it MUST NOT become a prerequisite for primary `M → D` migration verification or redefine expected migration transformations. Classify each span as naming, documentation/formatting, executable, or unresolved. Do not use a commit title as proof of classification.

A bridge permits attribution, not erasure. Check the file's `B → D` trajectory as well as its `M → D` migration transformation. Every bridge edit remains visible in the manifest. A pre-existing executable delta is reported even when migration preservation subsequently passes. If the earlier change cannot be adequately explained, the affected overall conclusion remains blocked.

A file absent from `B` but introduced before migration needs its complete evidenced introduction as a secondary origin. It remains a target-side addition in master accounting; do not manufacture a master counterpart.

### 5.2 Exact transformations

For each logical file pair, prepare the smallest exact sequence of edits justified by the frozen claim/authorisation evidence. Permitted forms include exact path moves and specific package/import/type-name/configuration/prose replacements, **only when those exact changes were authorised and claimed**.

Every edit is bound to a complete input object. Use zero-based byte offsets with an exclusive end and exact old/new bytes, or a uniquely constrained byte-context operation expanded to such offsets during preparation. The default is no content change and no mode change.

```yaml
# Non-executable edit template; all null inputs require preparation.
edit_id: E000001
stage_input_object_id: null
stage_input_sha256: null
location_kind: null
start_byte: null
end_byte_exclusive: null
old_bytes_base64: null
new_bytes_base64: null
expected_count: 1
claim_id: null
independent_permission_ref: null
expected_stage_output_sha256: null
```

At each stage, confirm the advertised old bytes at the declared range and expected occurrence count in its declared context. Apply edits against the specified stage input, reject overlaps, and compute the next full output. For multiple edits against a single input, validate all ranges first and apply them from highest offset to lowest. Do not silently relocate an edit when context differs.

Generate the expected output before making the comparison verdict. Store the transformation definition and its digest, then compare the entire resulting byte stream with the retrieved target. Expected hashes must be computed from the baseline plus justified edits, not copied from the target.

A transformation must not contain an unrelated deletion, logic rewrite, wildcard string replacement, uncontrolled regex, comment-stripping pass, whitespace/EOL normalisation or an arbitrary replacement by target bytes. An unexpected difference becomes a finding; the executor never extends the edit list to absorb it.

### 5.3 Protected and deferred content

Load the exact protected set from the frozen action map and relevant evidence. At the preparation observation, the migration ledger protects applied Flyway contents, stable `MS-*` identities and historical evidence, including the following examples:

Historical notification failure FQCNs, SQL/table/column identities and lock identities also require their applicable exact checks. This list is a navigation aid, not a replacement frozen authority source or an exhaustive current allowlist.

Preserve protected bytes at their corresponding occurrences; unchanged aggregate counts alone are insufficient. Package/import edits must not leak into protected strings that happen to share the old name. Record known legitimate residuals by exact path, occurrence, reason and owning deferred/protected obligation.

Only claimed changes are required. For example, deferred `GR-REN-03` test renaming and deferred `GR-REN-02-02` comments must not be treated as missing completed work. If those files unexpectedly changed anyway, their differences still require accounting.

## 6. GR-VV-03 — validate the method, then verify closed regions

### 6.1 Falsify the checking method first

Before accepting region receipts, establish that the exact checker/procedure rejects deliberate corruption in isolated scratch fixtures. Do not alter product files or run Maven/Actions for these negative controls. Record the method version/digest, fixture inputs, expected result and actual result. A later change to the method invalidates dependent receipts until revalidated.

Required controls include:

| Deliberate fixture condition | Expected outcome |
|---|---|
| Identical bytes/type/mode; or only the declared rename/edit | Pass the applicable check. |
| Remove a baseline file; omit an inventory row; duplicate a mapped endpoint | Fail coverage or identity. |
| Truncate a file tail; remove an interior method/paragraph | Fail full-content equality. |
| Change a same-length operator, literal or return value | Fail full-content equality. |
| Alter a protected string while making valid package/import edits | Fail protection/content. |
| Keep both old and new owner paths without a claimed copy | Fail path/identity obligations. |
| Change only file mode, EOL bytes or final newline without permission | Fail the relevant exact check. |
| Omit one claimed edit in a shared consumer | Fail that file and dependent claim. |
| Supply truncated tree/blob evidence or unknown object bytes | Block; never treat as an empty or passing file. |
| Hide a non-naming executable change in the master bridge | Prevent the no-logic-change conclusion. |
| Present a valid historical rename commit but a target tree without it | Fail the live-path/content obligation. |
| Move the branch to an undeclared target during execution | Invalidate live freshness; do not certify the new head. |
| Place one corrupt file inside an otherwise valid deterministic region | Fail that file and the affected region invariant; preserve passing evidence for unrelated files only when independence is mechanically established. |

Method validation is validation of the audit mechanism only. It is not application testing.

### 6.2 Whole-tree fast path

After the pinned baseline/target trees are enumerated, mechanically partition entries by exact object/type/mode/path evidence. Same immutable objects with equal modes enter the equality fast path where no unsatisfied claim requires a different path/content obligation.

Generate all fast-path file rows/results in one set operation. Do not open one execution packet per identical file.

### 6.3 Closed-region execution algorithm

For one `READY` deterministic region:

1. Check snapshot, region, method, manifest and claim digests.
2. Resolve every declared endpoint from the complete pinned trees and verify the region's exact finite file/claim set.
3. Retrieve complete bytes only where object equality cannot already establish the required content fact.
4. Reconstruct all declared bridges and exact transformations from independently justified inputs; validate every edit range/count before applying it.
5. Produce expected output bytes/digests for every changed file in the region and compare them with the complete target objects.
6. Prove region-wide set invariants: no missing/extra member, no undeclared changed endpoint, no unresolved in-region mapping, no prohibited old/new duplicate, and all protected/residual obligations satisfied.
7. Mechanically emit one result row per file and update all linked claim obligations from those exact results.
8. Record extra/missing bytes, mode/type/path mismatches and protected-identity failures as findings without widening the allowed transformation.
9. Save one immutable region receipt plus per-file result references; checkpoint only through the separately authorised path.
10. On a mismatch, isolate the smallest affected file/claim/exception set. Preserve mechanically independent passing results; never rewrite history or absorb the discrepancy into the expected answer.

### 6.4 Exception execution

Exception packets handle ambiguous mapping, compatibility/protected identities, non-naming executable deltas, split/merge/delete cases, historical bridge uncertainty, incomplete evidence and other non-deterministic cases. Every exception is explicitly resolved as PASS, FAIL or BLOCKED.

An exception packet may contain multiple cases only when their evidence/dependency boundary is closed and each case retains a separate result.

Content reads and comparisons are read-only. The only writes are packet-declared audit artifacts; they never include the files being verified.

## 8. GR-VV-04 — claim reconciliation

A migration claim passes only when all its obligations resolve to passing evidence at `D`. Check every owner file, moved path, affected consumer and claimed protected/residual property. Do not stop at the renamed package directory.

Preparation must expand owner-directory claims against complete source trees at the relevant pre-migration/pre-leaf point, then reconcile them with the target. Deriving the expected owner list only from surviving target files would miss deleted files. Independently inspect the relevant source/consumer references and complete changed-path evidence; do not trust a claimed consumer count as its own proof.

Inspect all reference forms relevant to the specific claim: package/import/type references, named entry points, service/resource/configuration references and runtime-coupled identifiers where the claim includes them. Deferred test/configuration references remain explicitly deferred, not silently passed as migrated. Unknown reference consequences block that obligation rather than trigger migration expansion.

Retain both lineage evidence and live-tree results. A repair commit or successful original migration commit does not excuse checking current bytes. The Enquiry repair described in the migration ledger is a required regression scenario for this rule, not a pre-approved pass.

For operational ledgers added after `master`, verify the evidenced introduction and relevant checkpoint lineage against full blobs. Every earlier receipt, claim ID, evidence reference and repair note must remain represented or have an explicit evidenced successor. A compacted description is not proof that the omitted underlying data survives; retain and verify its immutable source references. Do not reconstruct or repair those records inside the audit.

## 9. GR-VV-05 — findings, closure and freshness

### Finding and receipt minimums

A finding records: stable ID; run/packet/file/claim IDs; category; severity; complete expected/actual object references; precise affected range or path; evidence digest; whether the source is complete; conclusions affected; hand-off destination; and disposition. Use categories such as `MISSING_FILE`, `UNEXPECTED_ADDITION`, `CONTENT_LOSS`, `UNPERMITTED_EDIT`, `EXECUTABLE_DELTA`, `PROTECTED_IDENTITY_CHANGE`, `MODE_OR_TYPE_CHANGE`, `DUPLICATE_OR_AMBIGUOUS_MAPPING`, `CLAIM_NOT_IN_LIVE_TREE`, `INCOMPLETE_EVIDENCE`, and `STALE_TARGET`.

A receipt records: immutable inputs and packet digest; method version; checks attempted and exact outcomes; expected/actual digests and sizes; command/tool exits; findings; output evidence digests; checked target; and separately reported test/build/runtime status. An error or missing check never becomes `PASS` through a default value.

### Closure predicates

Generate the final summary from canonical records and require:

```text
complete inventories AND exact two-sided set reconciliation
AND complete frozen-claim enumeration
AND every required file/claim check actually run
AND every claimed obligation has passing evidence
AND no unexplained baseline/target delta
AND no unresolved truncation, missing object, mapping or protected-identity finding
AND no unresolved failed/blocked check relevant to the requested conclusion
AND checking method validated for the operations used
AND live freshness explicitly reconciled
```

Additionally, `master_non_naming_executable_preservation = PASS` requires zero executable-content differences beyond validated naming edits since `B`. Independently authorised compatibility logic changes or pre-migration source additions do not satisfy that strict assertion; report their exact effect and use `DIFFERENT` or `BLOCKED` as supported by evidence. Do not change the requested assertion into “tests pass” or “the change seems harmless”.

Classified non-migration revisions can coexist with a narrower migration-preservation pass, but must be listed. They cannot turn the whole repository into “unchanged except naming”. A zero-claim snapshot must explicitly report that no migration claims were available; do not imply useful migration validation from a vacuous pass.

### Implementation re-entry handoff

After `GR-VV-05` produces the required successful conclusions, check the canonical migration ledger for `GR-REN-08..11` closure. Only when both verification and migration closure pass may the work file emit `implementation_handoff: READY`.

On `READY`, the next action is to reconcile the canonical implementation graph against the verified target/current tree, refresh `/IMPLEMENTATION.md`, and resume eligible READY implementation automatically under IMPLEMENTATION-RULES v2.0.

Any relevant failed/blocked verification result, unresolved migration defect or blocking design escalation emits `implementation_handoff: BLOCKED` instead.

### A live branch is not an immutable target

Re-read remote `development` before the final report or publication:

- If it is still `D`, record the observation time and exact SHA.
- If only separately authorised audit receipt/state files changed, compare the entire `D → current` delta and record every changed/added audit path and object. The claim ledger, product tree and checking rules must be unchanged. The substantive certificate still targets `D`; describe the later receipt-only head separately.
- If source, claims, protected inputs, checking rules or any other undeclared path changed, the old results remain historical evidence for `D`, not live certification. Open a new target/run and revalidate affected rows and dependent claims. Reuse earlier receipts only after input/obligation identities are proven unchanged; recompute global coverage.

Do not amend a run's target SHA in place. Do not manufacture a lineage merge to retain evidence. Capture is not a branch lock: another actor can move the branch after the final observation, so report an as-of identity, not indefinite currentness.

### Publication and restart

Publication is separate from read-only verification. When authorised, require a fresh exact publication parent, inspect potential automatic workflow triggers, and commit only declared audit files. Do not push when doing so would run unauthorised GitHub Actions. A commit-message skip convention must not be assumed to cover all workflow events.

Reconcile every post-`D` audit artifact addition rather than globally excluding the evidence directory. Do not put a receipt's own publication SHA or checksum inside itself. Its checked target and inputs are internal fields; its publication identity comes from the Git envelope or a later checkpoint.

On restart, validate the latest receipt and its manifests before resuming the next packet. Preserve completed and failed evidence. Changes to expected edits, authority inputs, claim membership, method version, object bytes or path mappings invalidate all dependent receipts; unchanged evidence need not be reread ritualistically.

## 11. Efficiency and validation-cost invariant

Verification effort SHOULD scale primarily with the number of deterministic transformation classes, closed verification regions, exception classes and actual counterexamples—not with the raw number of historical migration leaves or tracked files.

Every tracked file is still accounted for and every changed/claimed file is still exactly checked. The optimisation is that identical objects, deterministic transformations and set invariants are processed mechanically in bulk while human/agent reasoning is concentrated on exceptional evidence.

Leaf/file count is evidence cardinality, not a mandate for repeated reasoning.
