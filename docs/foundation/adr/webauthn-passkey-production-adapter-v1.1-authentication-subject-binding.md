# ADR-015 v1.1 — WebAuthn Authentication-Subject Binding Amendment

**Document ID:** ADR-015  
**Version:** 1.1  
**Status:** Accepted  
**Accepted:** 28 August 2026  
**Amends:** ADR-015 — WebAuthn / Passkey Production Adapter  
**Depends on:** MS-PROT-028 through v1.3, MS-PROT-063, ADR-014, ADR-015 v1.0  
**Scope:** WebAuthn user-handle / Main Street Identity binding and Spring `PublicKeyCredentialUserEntity` persistence boundary  
**Purpose:** Define the approved production relationship between the WebAuthn user handle and Main Street semantic Identity without allowing WebAuthn, Spring Security or authentication persistence to become merchant/business authority.

---

## 1. Context

ADR-015 v1.0 selected Spring Security WebAuthn as Main Street's replaceable ceremony and cryptographic-verification adapter while preserving Main Street ownership of Identity, Session, Merchant Scope, merchant relationships and business authorisation.

IMP-04 has since established durable Main Street-owned persistence for Spring WebAuthn `CredentialRecord` state.

Production completion of Spring's `PublicKeyCredentialUserEntityRepository` requires one explicit decision that ADR-015 v1.0 intentionally did not make: what the WebAuthn `user.id` / user handle means relative to Main Street semantic Identity.

The accepted higher-layer constraints remain:

```text
Identity
    != WebAuthn credential
    != Session
    != Merchant Scope
    != Merchant Controller relationship
    != role / privilege / entitlement
```

A WebAuthn user handle is therefore an authentication-infrastructure identifier, not business authority.

---

## 2. Decision

Main Street SHALL use a distinct Main Street-generated opaque **WebAuthn Authentication Subject Handle** for each active WebAuthn authentication subject.

For the initial production model:

```text
Main Street Identity
        1
        |
        0..1 active
WebAuthn Authentication Subject Handle
        1
        |
        0..N
WebAuthn credentials / passkeys
```

The active WebAuthn Authentication Subject Handle is mapped one-to-one to exactly one Main Street Identity.

Multiple passkeys registered for the same Identity SHALL reference the same active WebAuthn Authentication Subject Handle.

The handle MUST NOT be the encoded Main Street semantic Identity identifier and MUST NOT derive authority from possession or knowledge of the handle.

---

## 3. Handle Properties

The WebAuthn Authentication Subject Handle SHALL be:

- generated by Main Street rather than selected by the browser/caller;
- opaque to callers and downstream business logic;
- non-empty and within the WebAuthn maximum user-handle size of 64 bytes;
- free of username, email address, merchant identifier, civil identity data and other directly identifying/business-authority content;
- stable for the active WebAuthn authentication subject while that binding remains active;
- independent of any individual credential identifier.

The exact byte length and storage encoding are implementation details provided these invariants hold.

---

## 4. Identity Binding Invariants

The durable binding SHALL preserve:

1. one active handle resolves to exactly one Main Street Identity;
2. one Main Street Identity has at most one active WebAuthn Authentication Subject Handle in the initial implementation;
3. an existing handle MUST NOT be rebound silently to another Identity;
4. creation of another credential for the same Identity MUST NOT manufacture another semantic Identity;
5. deletion of one credential MUST NOT delete the Identity or unrelated credentials for the same handle;
6. changing a Merchant Controller relationship MUST NOT alter this Identity binding merely because merchant authority changed;
7. recovery, rebinding, rotation or replacement of an authentication subject remains separately governed where it changes account-control or trust semantics.

The binding is authentication evidence/infrastructure state only.

---

## 5. Spring User Entity Boundary

Spring Security's `PublicKeyCredentialUserEntity` is a technical WebAuthn representation.

Main Street MAY persist the Spring-required fields:

```text
user handle (`id`)
name
optional display name
```

subject to these rules:

- `id` is the opaque WebAuthn Authentication Subject Handle;
- `name` and `displayName` are human-readable authentication-facing attributes only;
- neither `name` nor `displayName` establishes Main Street Identity equality;
- a username/email-like value MUST NOT become Merchant Scope, Controller authority, role or privilege;
- Spring repository lookup requirements do not transfer semantic Identity ownership to Spring Security.

A persistence adapter MAY store the Identity reference beside the technical user entity solely to resolve the approved one-to-one authentication-subject binding. That reference does not become a browser credential or business-authority claim.

---

## 6. Authentication Resolution

After Spring WebAuthn successfully verifies a credential:

```text
verified WebAuthn user entity
        ↓
opaque Authentication Subject Handle
        ↓
current durable handle -> Identity binding
        ↓
authenticated Main Street Identity evidence
        ↓
HumanSessionEstablishmentService
        ↓
fresh independent Main Street Session Credential
```

The existing ADR-015 session boundary remains mandatory.

Spring `GrantedAuthority`, `SecurityContext`, `HttpSession`, username or display name MUST NOT bypass the durable handle-to-Identity binding or Main Street Session establishment.

---

## 7. Merchant Authority Remains Downstream

Successful handle-to-Identity resolution does not establish:

- Merchant Scope;
- Merchant Controller relationship;
- Merchant Membership;
- role;
- privilege;
- Commercial Entitlement;
- capability permission;
- Operational Eligibility.

Those remain current downstream authority checks under the accepted semantic corpus.

---

## 8. Rejected Alternatives

### 8.1 Semantic Identity identifier used directly as WebAuthn handle

Rejected because it unnecessarily couples Main Street semantic Identity representation to a protocol-facing authentication identifier and constrains future Identity/authentication evolution.

### 8.2 Credential-local user handles

Rejected for the initial model because WebAuthn user handles represent the relying-party user account; assigning independent handles to each credential would complicate multi-passkey continuity and risk credential identity becoming account identity.

### 8.3 Deterministic HMAC/derived handle from Identity identifier

Rejected for the initial model because it retains representational coupling and introduces avoidable key-rotation/recovery complexity while offering no required semantic benefit over a durable opaque binding.

---

## 9. Persistence and Concurrency Requirements

The production persistence boundary SHALL enforce at least:

```text
unique active user handle
unique active Identity binding
unambiguous username lookup where Spring requires username lookup
1..64-byte user-handle constraint
no silent handle -> Identity rebinding
```

If a repeated save presents the same handle and Identity binding, technical human-readable user-entity attributes MAY be updated without changing the binding.

If the same handle is presented with a different Identity, or the same active Identity is presented with a different handle outside an explicitly governed replacement flow, persistence MUST fail closed.

---

## 10. Falsification Criteria

The implementation is non-conforming if any of the following can occur:

1. WebAuthn `user.id` is the semantic Identity identifier merely by representation reuse;
2. a username/email or display name determines Identity equality;
3. one active handle resolves ambiguously to multiple Identities;
4. an existing handle can be silently rebound to another Identity;
5. one Identity can acquire multiple simultaneously active handles without separately governed semantics;
6. credential deletion deletes semantic Identity or unrelated credentials implicitly;
7. successful WebAuthn resolution grants Merchant Scope/Controller/role/privilege authority;
8. Spring session/authority state bypasses Main Street Session establishment;
9. caller-selected PII/business identifiers are persisted as the opaque user handle.

---

## 11. Initial Implementation Shape

The smallest implementation child authorised by this amendment is:

```text
MainStreet-owned PublicKeyCredentialUserEntityRepository adapter
        +
opaque Authentication Subject Handle persistence
        +
unique active handle <-> Identity binding
        +
Spring-required id/name/displayName lookup
        +
WebAuthnIdentityReferenceAuthority backed by that binding
```

This child MUST NOT introduce browser filter-chain delivery, CSRF mechanics, account recovery, authentication-subject replacement/rotation, step-up implementation, high-risk hardware-attestation policy or merchant-authority shortcuts.

---

## 12. Deferred Scope Preserved

This amendment does not resolve:

- account/control recovery (`ADR-014-DQ-004`);
- exact CSRF implementation (`ADR-014-DQ-005`);
- session-cache technology (`ADR-014-DQ-007`);
- device-key storage/hardware binding (`ADR-014-DQ-008`);
- high-risk hardware/security-key requirement (`ADR-014-DQ-002`);
- CSP/Trusted Types profile (`ADR-014-DQ-017`);
- future WebAuthn authentication-subject replacement/rotation/rebinding semantics.

---

## 13. Approval Record

The design escalation compared direct semantic-Identity encoding, a separate opaque one-to-one authentication subject, credential-local handles and a lightweight hybrid persistence shape.

Manual approval was received on 28 August 2026 for the recommended hybrid:

> use a Main Street-generated opaque authentication-subject handle, one-to-one with Identity; multiple passkeys for the Identity share the handle; the handle has no independent business semantics and does not require a heavyweight WebAuthn User domain object.

This amendment formalises only that approved recommendation.
